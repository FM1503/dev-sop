# 验收测试纪律（量化版）

本规范是 dev-sop 流程中阶段 4 / 验收阶段强制遵循的测试纪律，由 `hooks/test-guard.js`（PreToolUse on Bash）硬性执行。定位与 `references/design-rules.md`（UI 设计规范）并列：design-rules 管"界面写得对不对"，本规范管"测试跑得对不对"。

## 1. 测试金字塔与耗时预算

按成本从低到高、数量从多到少分层执行，**能低层验证的不上高层**：

| 层级 | 内容 | 耗时预算 | 定位 |
| --- | --- | --- | --- |
| 静态检查 | 语法检查、lint、类型检查（`node --check`、eslint、tsc 等） | 秒级 | 每次改动后必跑 |
| 单元测试 | 单函数/单模块行为验证 | 分钟内 | **主力**，测试数量最多 |
| 集成测试 | 多模块协作、真实 IO | 按需 | 仅覆盖模块间契约，不重复单元覆盖 |
| 浏览器 / E2E | 真实浏览器端到端 | 最后跑、最少跑 | **仅 UI 验收项**专用 |

来源说明（业界共识）：
- Martin Fowler《Practical Test Pyramid》实践测试金字塔：底层多而快、顶层少而慢。
- Google Testing Blog《Just Say No to More E2E Tests》：E2E 昂贵、脆弱、应最少使用。
- XP（Extreme Programming）"十分钟构建"：整场反馈循环必须控制在分钟级。

## 2. 硬预算（test-guard.js 强制）

- **单条测试命令 ≤ 2 分钟**：调用 Bash 跑测试时必须显式设置 `timeout` ≤ 120000ms；显式超过 120000ms 的测试命令会被 hook 直接 deny。
- **整场验收 ≤ 10 分钟**：所有验收测试命令累计耗时不超过 10 分钟，超出说明测试分层出了问题。
- **超预算豁免**：确需长跑测试时，必须先用 `AskUserQuestion` 向用户说明理由并获得批准，然后在**项目根**创建 `.dev-sop-approve-longtest` 标记文件（空文件即可）。该文件存在期间，test-guard 对测试命令放行；事后应删除恢复纪律。

## 3. fail-fast 纪律

- **首条失败即停**：测试一失败立即停止后续命令，先修复，再**从失败处续跑**。
- **禁止重跑已绿项**：已通过的测试不需要在迭代中反复重跑；全量回归仅在交付前跑一次。

## 4. 测试选择（迭代修复）

迭代修复过程中只跑**受影响的测试**，手段任选：

- 文件映射：改动 `src/foo.js` 只跑对应测试文件 `tests/foo.test.js`；
- 增量模式：`jest -o` / `--onlyChanged`、`pytest --lf` 等框架提供的受影响用例选择；
- 具体用例名：`pytest tests/test_a.py::test_case1`、`jest -t "用例名"` 等。

**全量回归仅在交付前跑一次**，不是每次改动的默认动作。

## 5. 反冗余

- **一条验收标准对应一个针对性测试**：不写验证不了任何验收标准的"凑数测试"。
- **同一验收项不得在多层重复覆盖**：单元测试已覆盖的逻辑不再写集成测试、更不写 E2E 重复验证。
- **任务书测试计划表之外的测试禁止执行**：跑表外测试既浪费时间，也掩盖计划缺失的问题——发现计划缺口应回到任务书补条目，而不是直接跑。

## 6. 后台 / 监听禁令

测试命令禁止以 `run_in_background` 方式执行，禁止 `--watch` / `--watchAll` / `nodemon` / `-w /` 等监听模式（test-guard.js 对 Bash 命令强制拦截，deny）。测试必须是**前台、有限次、带显式 timeout** 的执行。
